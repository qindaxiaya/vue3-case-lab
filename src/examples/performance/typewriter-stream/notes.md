# 流式打字机

## 1. 现象与场景

流式回答一收到 token 就整段上屏，文字「跳」着出现；网络快时一次蹦出十几个字，像卡了一下。

复现：分别点「直接拼接」和「rAF 平滑」再「重新开始」，对比「单帧最大跳变」：前者 2~4 字，后者稳定 ≤3 字。

## 2. 原理

网络层是生产者，屏幕是消费者。token 到达速度不均匀，如果收到就渲染，单帧可能追加一大段；正确做法是先把内容放进缓冲区（backlog），由 rAF 以固定预算逐帧消费。

「已接收」和「已显示」必须是两个变量：前者是网络进度，后者是屏幕进度，差值就是积压。积压过多时可以自适应加速（每帧多取一点），但不能无限追，否则又变成整段跳。

## 3. 关键代码

```ts
// 1. 网络层只入缓冲，不直接上屏
received.value += text
backlog.value += text.length

function tick(): void {
  if (backlog.value > 0) {
    // 2. 每帧固定预算，屏幕推进速度稳定
    const take = Math.min(3, backlog.value)
    shownLen.value += take
    backlog.value -= take
  }
  rafId = requestAnimationFrame(tick)
}

// 3. 停止时先取消 rAF，再一次吐出剩余内容，避免丢字
onUnmounted(() => {
  cancelAnimationFrame(rafId)
  shownLen.value = received.value.length
})
```

## 4. 数据对比

| 指标 | 直接拼接 | rAF 平滑 |
|---|---|---|
| 接收 / 显示（2.2s） | 23 / 23 字 | 23 / 23 字 |
| 单帧最大跳变 | 2~4 字 | ≤3 字 |
| 积压 | 通常 0（到即上屏） | 随到达速度波动后归零 |
| 渲染节奏 | 跟随网络 | 跟随屏幕刷新 |

测量方式：Chrome headless 1200×900，切换模式后点「重新开始」，等 2.2s 读取面板四个计数。单帧跳变由 Demo 在每帧消费时记录最大值。

## 5. 追问与边界

**Q：为什么不用 `setInterval(15ms)` 加一个字？**
可以，但定时器与刷新不同步，容易在两次绘制间堆叠；rAF 与屏幕同步，后台标签还会自动停。

**Q：积压一直涨怎么办？**
提高每帧消费量（如积压的 1/6，上限 6 字），或在网络层做背压；否则内存与渲染压力都会上升。

**Q：Markdown 流式渲染要注意什么？**
半截的 `**加粗**`、未闭合的代码块会闪烁或让高亮器报错；只渲染到最后一个完整行/段落，或延迟到标点再解析。

坑：停止时只 abort 请求、不取消 rAF，回调仍在操作已卸载组件。边界：打字机只是视觉平滑，不改变真实生成速度；对时效要求高的内容应直接显示。
