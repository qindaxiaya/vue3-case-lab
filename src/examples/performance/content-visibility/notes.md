# content-visibility 长列表

## 1. 现象 / 场景

管理后台一次展示 3000 条日志卡片，数据不能分页。打开页面先白屏一阵，滚动时也发涩；明明屏幕里只放得下五六条，浏览器却把三千条都排了一遍。

复现步骤：

1. 打开案例，默认模式显示 3000 条卡片。
2. 点「重测两种模式」，等两种模式各跑三次，读取「默认」「跳过屏外」两列耗时。
3. 手动在列表里滚动，确认滚动条高度稳定、卡片按需出现。

## 2. 原理

浏览器渲染一帧要经历样式计算、布局、绘制、合成。默认情况下，即使元素在滚动容器外，只要它在 DOM 里，就会参与样式计算和布局；列表越长，首次布局和滚动时的重排成本越高。

`content-visibility: auto` 告诉浏览器：这个元素不在视口附近时，可以跳过它的内容渲染，只保留一个占位。滚动到附近再补上。跳过的是子树的布局与绘制，元素本身的盒子仍然存在。

占位高度由 `contain-intrinsic-size` 提供。不写预估高度时，屏外元素按 0 处理，滚动条会突然变短、滚动位置乱跳。案例的卡片固定 64px，所以写 `auto 64px`：浏览器第一次渲染后记住真实尺寸，之后用记忆值，尺寸变化时再更新。

## 3. 方案：关键代码

```ts
// ① 换 key 强制重建，两种模式都从零开始，避免复用旧节点影响测量
listKey.value++
const startedAt = performance.now()

await nextTick()
// ② 主动读一次尺寸，让布局立即发生，而不是被浏览器拖到下一帧
const el = listEl.value
if (el) void el.offsetHeight
await nextFrame()

// ③ 两帧之后再停表，覆盖样式计算、布局和绘制提交
return performance.now() - startedAt
```

```css
.list--cv .cv-item {
  content-visibility: auto;
  /* 与真实卡片高度一致，滚动条才不会跳 */
  contain-intrinsic-size: auto 64px;
}
```

测量函数会对同一模式跑三次，排序后取中间值，避免某一次被后台任务打断导致数字失真。

## 4. 数据对比

| 指标 | 默认渲染 | 跳过屏外 | 测量方式 |
|------|----------|----------|----------|
| 重建耗时（中位数） | 99.4 ms | 49.9 ms | 案例「重测两种模式」 |
| 提速 | — | 1.99× | 默认耗时 ÷ 跳过屏外耗时 |
| 实际节点数 | 3000 | 3000 | `querySelectorAll('.cv-item').length` |
| 滚动高度 | 192016 px | 192016 px | 列表 `scrollHeight` |

测量说明：

- 环境：Chrome headless 155、1200×900、Vite dev；3000 条固定数据，每条 64px。
- 取样：两种模式各 3 次取中位数，三次结果为 99.7 / 92.7 / 99.4ms 与 49.4 / 49.9 / 50.1ms。
- 节点数不变，说明省下的是屏外内容的布局与绘制，不是删数据；滚动高度一致，说明预估高度生效。

## 5. 追问与边界（面试高频）

- Q: 它和虚拟列表有什么区别？ → A: 虚拟列表不创建屏外节点；`content-visibility` 节点都在，只是跳过渲染。前者省内存，后者改造成本低。
- Q: 不写 `contain-intrinsic-size` 会怎样？ → A: 屏外内容按 0 高度占位，滚动条长度和滚动位置会跳，锚点定位也会错。
- Q: 为什么读 `offsetHeight`？ → A: 强制浏览器立刻完成布局，否则测量可能只算到 DOM 更新，没算到真正的布局开销。

踩坑：

1. 预估高度和真实高度差太多 → 滚动条抖动，滚动到附近时内容高度突变。
2. 在屏外元素上反复 `getBoundingClientRect` → 浏览器被迫渲染它，优化失效。
3. 给频繁增删的列表用固定预估高度 → 每次高度变化都要重新记忆，收益下降。

边界：需要精确读取屏外元素尺寸、打印、截图、锚点定位到屏外内容时不适合；内容高度随图片加载变化的列表要配合 `ResizeObserver` 或固定宽高比。这个案例的收益来自「跳过布局与绘制」，JavaScript 创建 3000 个节点的成本仍然存在。
