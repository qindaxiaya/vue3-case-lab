# PermissionMenu：菜单别和权限各写一份

## 1. 现象 / 场景

后台菜单写死在模板里，权限又写在路由守卫或接口里。访客登录后仍能看到「用户管理」，点进去才被拦；改一次权限要改菜单、路由、按钮三处，总漏一处。

复现步骤：

1. 打开案例，默认「编辑」角色：左侧写死菜单 7 项，右侧权限菜单 4 项、2 个分组。
2. 切「访客」：左侧仍是 7 项，右侧只剩「概览」1 项、1 个分组。
3. 切「管理员」：右侧 7 项、3 个分组全部出现。
4. 点「重置」回到编辑角色。

## 2. 原理

菜单是权限数据的投影，不是另一份手写配置。每个叶子菜单声明自己需要的权限点，渲染前按当前角色过滤。

分组本身不是权限项：它只是容器，应该在还有可见子项时保留，没有可见子项时一起剪掉。否则访客会看到一个「系统管理」分组，点开却是空的。

角色切换后必须重新过滤整棵树，不能缓存上一次的菜单；路由守卫和接口校验仍然要做，前端菜单只负责「看不看得到」，不是安全边界。

## 3. 方案：关键代码

```ts
//! 叶子按权限点过滤，分组按子项剪枝
function filterMenu(nodes: MenuNode[], permissions: Set<string>): MenuNode[] {
  return nodes.flatMap((node) => {
    if (node.children) {
      const children = filterMenu(node.children, permissions)
      return children.length ? [{ ...node, children }] : []
    }
    return permissions.has(node.permission) ? [node] : []
  })
}

//! 角色一变就重新过滤整棵树，菜单不缓存旧结果
const visibleTree = computed(() => {
  const permissions = new Set(ROLE_PERMISSIONS[role.value])
  return filterMenu(MENU_TREE, permissions)
})

//! 分组数量只数还有子项的分组，空分组不会留在界面上
const groupCount = computed(() =>
  visibleTree.value.filter((node) => node.children?.length).length,
)
```

三处关键选择：

1. 递归函数先处理分组再处理叶子：分组的存亡由过滤后的子项决定，不是由分组自己的权限点决定。
2. `permissions` 用 `Set`，叶子判断是 O(1)；角色切换时重新构造，不修改原权限表。
3. 左侧写死菜单保留全部 7 项，是为了让「菜单和权限各写一份」的漂移肉眼可见，不是推荐写法。

## 5. 追问与边界（面试高频）

- Q: 菜单过滤了，路由还需要守卫吗？ → A: 需要。用户可以直接输 URL，菜单只是视觉层，守卫和接口才是权限边界。
- Q: 分组要不要也配权限点？ → A: 一般不需要。分组按子项剪枝更稳；如果分组本身有独立入口，再给它加权限点。
- Q: 权限点从哪来？ → A: 登录后由后端返回权限码，前端按码过滤；不要把角色和菜单写死在前端。

踩坑（≤3 条）：

1. 只过滤叶子、不剪分组：访客会看到空分组 → 分组必须按过滤后的子项决定去留。
2. 角色切换后复用旧菜单：菜单停留在上一个角色 → 用 `computed` 依赖角色重新过滤。
3. 把菜单当权限边界：菜单藏了，接口仍能调 → 接口必须二次校验。

边界：更细的后台会用后端返回的权限码动态注册路由，退出登录要移除动态路由；本例只演示菜单树的过滤与剪枝，路由守卫见 practice/route-rbac 案例。
