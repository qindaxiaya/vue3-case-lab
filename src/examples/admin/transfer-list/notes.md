# TransferList：穿梭框别把禁用项也移走

## 1. 现象 / 场景

权限分配用穿梭框时，几个边界最容易出错：搜了「报表」再点全选，没显示的权限也被选中；系统设置明明是禁用项，批量移动还是把它带走；移回后没有清空已选，下一次移动又重复处理。

复现步骤：

1. 打开案例，源列表 6 项、目标 0 项，其中「系统设置」是禁用项。
2. 点「全选可移」，已选 5 项，禁用项没有被选中。
3. 点「移动选中」，源剩 1 项（禁用项）、目标 5 项，已选归零。
4. 点「重置」，回到源 6、目标 0。
5. 搜索「报表」，可见 2 项；全选并移动后，源 4、目标 2。
6. 清空搜索，在目标侧选中第一项并点「移回」，源 5、目标 1。

## 2. 原理

穿梭框同时维护四份状态：源列表、目标列表、源已选、目标已选。搜索只是显示层的过滤，不能改动任何一份选择；否则用户清空搜索后会发现之前选的东西莫名其妙没了。

全选要同时满足两个条件：当前可见、未被禁用。只按「源列表全部」选，会把搜索隐藏的项和禁用项一起选上；移动时再按已选 id 从源列表删除、追加到目标，最后清空源已选，避免下一次重复移动。

计数不要手写。源数量、目标数量、已选数量、禁用数量、可见数量都应该从列表和选择派生，任何一次移动或搜索后自动更新，才不会出现「列表 5 项、计数还写 6」。

## 3. 方案：关键代码

```ts
//! 全选只选当前可见且未禁用的源项，禁用项不参与批量移动
function selectAllSource(): void {
  selectedSource.value = sourceVisible.value
    .filter((item) => !item.disabled)
    .map((item) => item.id)
}

//! 按 id 移动，移动后清空源已选，避免下一次重复处理
function moveSelected(): void {
  const ids = new Set(selectedSource.value)
  const moving = source.value.filter((item) => ids.has(item.id) && !item.disabled)
  const movingIds = new Set(moving.map((item) => item.id))
  source.value = source.value.filter((item) => !movingIds.has(item.id))
  target.value = [...target.value, ...moving]
  selectedSource.value = []
}

//! 搜索只影响显示，不改变已选；隐藏的已选项仍然保留在数组里
const sourceVisible = computed(() => source.value.filter(matches))
const targetVisible = computed(() => target.value.filter(matches))
```

三处关键选择：

1. `selectAllSource` 从 `sourceVisible` 里取，搜索隐藏的项不会被选中；再过滤 `disabled`，禁用项永远不会进入批量操作。
2. `moveSelected` 用 id 集合移动，避免按索引删除时越界；移动后只清空源已选，目标已选不受影响。
3. `sourceVisible` / `targetVisible` 是派生列表，搜索变化只改显示，`source` 和 `target` 本身不动。

## 5. 追问与边界（面试高频）

- Q: 搜索时要不要保留已选？ → A: 要。搜索只是过滤显示，已选是业务状态；清空搜索后已选项应该还在，计数也要继续算上隐藏项。
- Q: 全选为什么要排除禁用项？ → A: 禁用代表当前不可分配，批量操作不能绕过单条限制；全选只选「可移动」的项。
- Q: 移动后为什么必须清空已选？ → A: 不清空的话，下一次点移动会拿旧 id 再处理一遍；列表里已经没有了，但逻辑上仍会尝试。
- Q: 计数为什么要派生？ → A: 手写计数迟早和列表不同步；源、目标、已选、禁用、可见都能从状态算出来。

踩坑（≤3 条）：

1. 全选直接取源列表全部：搜索隐藏项和禁用项一起被选中 → 从可见列表取，再过滤禁用。
2. 搜索时清空已选：用户切回全部发现选择丢了 → 搜索只改显示，不动选择数组。
3. 移动后不清空已选：下一次移动重复处理旧 id → 移动成功立即清空对应侧选择。

边界：本例只做单页内存穿梭，没有后端保存、拖拽排序、分组和虚拟滚动；真实项目里源 / 目标通常是分页接口，移动要等接口成功后再更新本地列表，失败还要回滚。
