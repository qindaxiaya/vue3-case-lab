# FormDrawer：新增编辑共用一个抽屉

## 1. 现象 / 场景

后台的新增和编辑各写一套弹窗，字段一改两边不同步；用户填了一半点遮罩，内容直接没了；保存接口失败，抽屉已经关了，只能重新填。

复现步骤：

1. 点「新增用户」打开抽屉，直接点保存，名称和负责人各出现一条校验错误。
2. 填好名称、负责人、状态后保存，抽屉关闭，列表从 3 条变 4 条。
3. 编辑第一行，改完名称点取消，出现「有未保存修改」保护条。
4. 点「放弃并关闭」，列表内容不变；打开「模拟保存失败」再保存，失败后抽屉不关，错误留在抽屉里。

## 2. 原理

新增和编辑的差别只有「初始值」和「提交到哪个接口」，表单结构、校验、关闭保护都一样。把两者收进一个抽屉，用 `editingId` 区分模式，脏数据判断只比较当前值和打开时的快照。

关闭保护不能只看「表单有没有值」：用户可能打开后什么都没改，这时直接关没问题；也可能只改了一个字，这时应该先问一句。用原值快照比较，比「监听所有输入」简单，也不会被撤销操作骗过去。

保存失败不关抽屉，是因为用户填的内容比一次重试更贵。保留表单和错误，用户改完就能原地点保存。

## 3. 方案：关键代码

```ts
//! 打开时复制一份原值，用来判断「有没有改过」
const original = ref({ name: '', owner: '', status: 'enabled' as Status })

const dirty = computed(
  () =>
    form.name !== original.value.name ||
    form.owner !== original.value.owner ||
    form.status !== original.value.status,
)

//! 有未保存修改时先显示保护条，不要直接关
function requestClose(): void {
  if (submitting.value) return
  if (dirty.value) {
    showDiscard.value = true
    return
  }
  closeDrawer()
}

//! 保存失败不关抽屉：保留表单和错误，让用户原地点重试
async function submit(): Promise<void> {
  if (submitting.value) return
  if (!validate()) return

  submitting.value = true
  submitError.value = ''
  await wait(500)

  if (failNext.value) {
    failCount.value++
    submitError.value = '保存失败：网络超时'
    submitting.value = false
    return
  }

  // 成功后才更新列表并关闭
  closeDrawer()
}
```

三处关键选择：

1. 新增和编辑共用 `form`，只换初始值，避免两套字段逐渐不一致。
2. 用快照比较脏数据，而不是「输入过就算脏」；用户改回原值也可以直接关。
3. 提交中 `requestClose` 直接 return，遮罩和关闭按钮都关不掉。

## 5. 追问与边界（面试高频）

- Q: 新增和编辑要不要拆两个组件？ → A: 字段和校验完全一样时共用一个，用模式区分；如果编辑有额外只读字段或不同提交接口，再拆。
- Q: 脏数据为什么要用快照比较？ → A: 「输入过」不等于「有修改」，用户改回原值也应该能直接关；快照比较更准确。
- Q: 保存失败为什么不清空表单？ → A: 用户填的内容最贵，保留表单和错误，重试成本最低。

踩坑（≤3 条）：

1. 只在点「取消」时判断脏数据：点遮罩、Esc、右上角关闭都能绕过 → 所有关闭入口统一走 `requestClose`。
2. 提交中允许关闭：请求还在跑，组件已卸载 → `submitting` 时锁住所有关闭入口。
3. 新增成功后没重置 `editingId`：下次打开编辑会串模式 → 打开新增时显式设回 `null`。

边界：本例没有做焦点陷阱和背景滚动锁；需要完整无障碍支持时用成熟组件库的 Drawer。表单字段很多时再考虑分组和折叠，不要一上来就做动态表单。
