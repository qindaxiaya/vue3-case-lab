# AuditLog：审计日志要能还原现场

## 1. 现象 / 场景

后台出了数据问题，翻日志只看到「操作成功」；失败的操作没记，用户手机号却明文躺在日志里。排查时既不知道谁改了什么，也不敢把日志发给别人。

复现步骤：

1. 点「新增订单」「修改金额」：简易日志出现 2 条成功记录。
2. 再点「删除订单（失败）」：简易日志仍是 2 条，审计日志变成 3 条。
3. 切「失败」筛选：只剩 1 条，展开后能看到失败原因。
4. 详情里手机号显示 `138****8000`，不是明文。

## 2. 原理

审计日志和普通调试日志不一样：它要能回答「谁、什么时候、对什么、做了什么、结果如何、改前改后是什么」。

失败操作同样重要，因为「删不掉」本身就是现场；只记成功，排查时会误以为用户没操作过。敏感字段要在写入或展示时脱敏，不能等导出时再处理。

日志只追加、不覆盖：每条记录有独立 id，筛选只影响展示，不修改原始数据。详情展开按 id 控制，避免多个条目同时展开。

## 3. 方案：关键代码

```ts
//! 审计日志只追加，不覆盖旧记录
function append(entry: Omit<AuditEntry, 'id' | 'time'>): void {
  auditLog.value = [
    { ...entry, id: nextId++, time: nowText(), phone: MASKED_PHONE },
    ...auditLog.value,
  ]
}

//! 失败操作也要写审计日志，否则出事时只看到成功记录
function removeOrder(): void {
  append({
    actor: '张三（运营）',
    action: '删除订单',
    target: '订单 #A1024',
    result: 'failed',
    reason: '订单已发货，不能删除',
    before: { 状态: '已发货' },
    after: { 状态: '已发货（未删除）' },
    phone: MASKED_PHONE,
  })
}

//! 筛选只影响展示，原始日志不动
const visibleAudit = computed(() => {
  if (filter.value === 'all') return auditLog.value
  return auditLog.value.filter((entry) => entry.result === filter.value)
})
```

三处关键选择：

1. `append` 统一生成 id 与时间，调用方只关心业务字段，不会出现两条记录抢同一个 id。
2. 失败分支和成功分支走同一个 `append`，避免「成功写日志、失败直接 return」的常见漏记。
3. 手机号在写入时就换成 `MASKED_PHONE`，展示层不需要再判断；真实项目也可以在服务端落库前脱敏。

## 5. 追问与边界（面试高频）

- Q: 审计日志和普通日志有什么区别？ → A: 审计日志面向追责与还原，要求结构化、不可篡改、保留变更前后；普通日志面向调试。
- Q: 失败操作为什么要记？ → A: 失败本身就是现场，能解释用户为什么没做成；只记成功会丢失关键上下文。
- Q: 脱敏放在前端还是后端？ → A: 落库前或返回前脱敏更稳；前端展示层也要兜底，避免调试接口把明文带出来。

踩坑（≤3 条）：

1. 失败分支直接 return：日志只有成功记录 → 成功失败走同一个追加函数。
2. 日志用覆盖写：只保留最后一条 → 用数组追加，每条独立 id。
3. 手机号明文展示：排查时泄露隐私 → 写入或展示前统一脱敏。

边界：真实审计日志通常落独立存储、只追加、带签名或哈希链；本例用内存数组演示字段与交互，不处理持久化和防篡改。
