# DynamicForm：动态行别用数组下标当 key

## 1. 现象 / 场景

采购单要支持一次填多行商品。用数组下标当 key 后，删掉中间一行，后面行的输入框内容错位；提交时只提示「有错误」，却不知道是哪一行，用户只能从头找。

复现步骤：

1. 打开案例，初始 2 行，两行都合法。
2. 点「添加一行」，变成 3 行，新行还是空的，合法数仍是 2。
3. 给新行填名称、数量、单价，合法数变成 3。
4. 删除中间行，剩 2 行，合法数仍是 2，剩余行 id 不重复。
5. 清空第 1 行名称后提交，错误 1 条、提交次数 0，错误行保留。
6. 填回名称再提交，错误 0 条、提交次数 1。
7. 点重置，回到 2 行、提交次数 0、状态「待填写」。

## 2. 原理

动态行的每一行都需要一个稳定身份。数组下标会随着删除变化，Vue 复用节点时就会把上一行的输入状态套到下一行；用自增 id 做 key，删除只按 id 过滤，其他行的身份不变。

校验结果也要写回行本身，而不是只存一个全局错误字符串。错误行保留在列表里、标红并显示原因，用户可以直接改；合法行清掉旧错误，避免上一次提交的错误一直挂着。

提交次数只统计真正成功的提交。有错误时只更新错误状态，不增加次数；全部合法才累加，这样「提交成功了几次」才是可信的。

## 3. 方案：关键代码

```ts
//! 每行分配自增 id，新增只追加，删除按 id 过滤
function addRow(): void {
  rows.value.push({
    id: nextId.value++,
    name: '',
    qty: '',
    price: '',
    error: '',
  })
}

function removeRow(id: number): void {
  rows.value = rows.value.filter((row) => row.id !== id)
}

//! 单行校验：名称非空、数量正整数、单价正数
function validateRow(row: FormRow): string {
  if (!row.name.trim()) return '请输入名称'
  const qty = Number(row.qty)
  if (!Number.isInteger(qty) || qty <= 0) return '数量为正整数'
  const price = Number(row.price)
  if (!Number.isFinite(price) || price <= 0) return '单价为正数'
  return ''
}

//! 提交时逐行校验，错误写回该行；全部合法才增加提交次数
function submit(): void {
  let errors = 0
  for (const row of rows.value) {
    row.error = validateRow(row)
    if (row.error) errors += 1
  }

  if (errors > 0) {
    statusText.value = `有 ${errors} 行需要修改`
    return
  }

  submitCount.value += 1
  statusText.value = '提交成功'
}
```

三处关键选择：

1. `addRow` 用 `nextId` 自增，删除后也不复用旧 id，`key` 始终稳定。
2. `removeRow` 按 id 过滤，不按数组下标 splice，避免删错行。
3. `submit` 把校验结果写回每一行的 `error`，错误行保留；`validCount` 实时从 `validateRow` 派生。

- 环境：本机 Chrome，案例页 `/cases/admin/dynamic-form`。

## 5. 追问与边界（面试高频）

- Q: 为什么不能用数组下标当 key？ → A: 删除中间行后，后面行的下标整体前移，Vue 会复用错误的节点，输入框内容错位；id 不随位置变化。
- Q: 删除行为什么要按 id？ → A: 下标在删除瞬间会变化，按 id 过滤不会误删其他行；新增行也不会复用已删除的 id。
- Q: 错误为什么要写回行里？ → A: 用户需要知道哪一行错了；只存全局错误数量，错误行无法定位，改起来只能从头找。
- Q: 提交次数为什么要等全部合法才加？ → A: 有错误时并没有真正提交成功，次数只统计成功提交，才能反映真实操作结果。

踩坑（≤3 条）：

1. 用数组下标当 key：删除中间行后输入内容错位 → 用自增 id。
2. 删除后 id 复用：新行拿到旧 id，key 冲突 → `nextId` 只增不减。
3. 有错误也增加提交次数：次数看起来成功了，实际没有 → 校验通过后再累加。

边界：本例是前端内存表格，没有后端批量保存、并发冲突和草稿恢复；真实项目里删除未保存行、服务端返回行级错误、提交失败回滚都需要额外处理。
