# auto-fit 自适应卡片网格

## 1. 现象 / 场景

卡片列表做响应式要维护一张手写断点表（几条媒体查询对应几种列数），每次调整卡片最小宽度都要重算全表，漏一条就在某个宽度区间露出大空白或横向溢出。

复现步骤：

1. 打开案例，切到「flex + 手写断点（旧）」模式。
2. 拖动右缘把手把容器从宽拖到窄，观察列数变化流水：每变一次列数就对应断点表里的一条规则，「媒体查询条数」恒为 5。
3. 切到「auto-fit（推荐）」，同样拖动一遍：列数随宽度平滑增减，「媒体查询条数」恒为 0。

## 2. 原理

`grid-template-columns: repeat(auto-fit, minmax(160px, 1fr))` 把「列数」从写死的数字变成引擎现算的量：布局阶段浏览器用容器可用宽度除以「最小轨道 160px + 间隙」，能整除放下几列就开几列；容器变窄放不下最后一列时整列消失，其余列用 `1fr` 把腾出的空间均分回去。整个「断点判定 + 列数重算」都发生在浏览器内部，CSS 里不出现任何手工数字。

手写媒体查询是同一件事的人肉版：每个屏宽区间写一条 `@media`，区间之内的布局是静态赋值。它的根本限制是查询条件只能跟视口走——组件被塞进侧栏、弹窗、分栏容器里时视口没变、容器已变，整张表对不上号；而且断点区间的数量随「列数档位」线性增加，本质是把连续问题离散化后再人肉采样。

浏览器侧的差异没有魔法：两种方案最终都由布局引擎算列，区别只是「判定断点的这张表」由引擎维护（auto-fit）还是由人维护（媒体查询）。

## 3. 方案：关键代码

以 `panel--auto`、`measureCols`（Demo.vue）定位：

```css
/* auto-fit：一行声明，0 条媒体查询 */
.panel--auto {
  display: grid;
  /* 为什么写在模板网页上：auto-fit 依赖内容自然流动，不能套在固定高度容器里 */
  grid-template-columns: repeat(auto-fit, minmax(160px, 1fr));
  gap: 0.5rem;
}
```

```ts
// ResizeObserver 回调里读真实列数（autofit 分支）
const tracks = getComputedStyle(el).gridTemplateColumns.trim()
// 1. 为什么用计算样式而不是自己除：auto-fit 的列数由引擎算，
//    不重新实现引擎的取整规则，读结果最可靠
// 2. 为什么放 ResizeObserver 而不是轮询：布局真的变了才需要重读，
//    回调由引擎在变化后发出，天然贴合
return tracks ? tracks.split(/\s+/).length : 1

// 3. 为什么跳过首轮回调：lastCols === -1 时只建立基线，
//    挂载时的第一次布局不算「断点跳变」，否则重置后指标永远从 1 起
if (lastCols >= 0 && next !== lastCols) {
  jumps.value++
  pushLog(`列数 ${lastCols} → ${next}（容器 ${width.value}px）`)
}
```

## 4. 数据对比

| 指标 | 错误（flex + 手写断点） | 正确（auto-fit） | 测量方式 |
|------|--------------------------|-------------------|----------|
| 媒体查询条数 | 5 条（720/600/480/360/兜底） | 0 条 | 静态统计：Demo 内断点表 `MEDIA_BREAKS` 与 CSS 声明数量 |
| 容器宽度响应 | 实时 | 实时 | `ResizeObserver` 回调读 `getBoundingClientRect().width`，四舍五入回显 |
| 当前列数 | 断点表求值 | 计算样式轨道数 | media 分支查 `MEDIA_BREAKS`；autofit 分支 `getComputedStyle('gridTemplateColumns')` 分段计数 |
| 断点跳变次数 | 每次列数变化 +1（来自 5 条手写规则） | 每次列数变化 +1（列数由引擎自然增减，0 条规则要维护） | `ResizeObserver` 回调里比较相邻两次列数，变化即 +1；「重置」按钮清零并重建基线 |

测量说明：

- 指标定义：「断点跳变次数」指本次重置以来，容器宽度连续变化时列数发生变化的累计次数；「媒体查询条数」是代码层面的静态规则数，不随拖动变化。
- 采集方式：`ResizeObserver` 监听可拖宽容器，回调内同步读取宽度与列数；跳变计数为相邻列数比较，非定时采样。
- 数据规模：8 张固定卡片，容器在 200px ~ 舞台宽度之间拖动。
- 环境：Chrome / Edge 近两年版本（需支持 grid 与 ResizeObserver），窗口或容器拖动改变了外层宽度同样会被计入。
- 取样：拖动轨迹不同则跳变次数不同，属连续事件的累计计数，无中位数概念；两次初始化状态一致即可复现（0 次起步）。
- 以 Demo 面板实测为准，本页不给出任何时间类数值。

## 5. 追问与边界

**Q：auto-fit 和 auto-fill 有什么区别？**
容器塞得下 3 列但只有 2 张卡时：auto-fit 把空出来的第 3 列折叠掉，2 张卡摊满整行；auto-fill 保留空轨道，2 张卡只占前 2 格。选哪个取决于「空位要不要摊开」的语义。

**Q：为什么卡片里还要 min-width: 0？**
网格轨道的隐式最小宽度是 auto（内容宽度），长单词或长链接会把轨道撑破。`minmax(160px, 1fr)` 显式给了最小值后配合文本换行（overflow-wrap）才真正收住。

**Q：auto-fit 能代替所有响应式网格吗？**
不能。需要与页面栅格严格对齐（比如 12 列栅格）、或最后一行必须保留空位占位时，固定 `repeat(N, minmax(0, 1fr))` + 少量断点更合适。auto-fit 擅长的是「内容驱动的卡片流」。

**Q：Flex 两端对齐加 justify-content 岂不是更简单？**
`justify-content: space-between` 处理最后一行的畸行会很尴尬（2 个元素被顶到两端中间留大洞），网格模型没有这个问题。

踩坑：

1. 触发条件：卡片里塞了不可换行的长内容 → 现象：列被撑破、溢出容器 → 修法：内容容器 `min-width: 0` + `overflow-wrap: anywhere`。
2. 触发条件：把 auto-fit 网格放进设置了固定高度的容器 → 现象：轨道拉伸、卡片高度不齐 → 修法：让网格按内容自然撑高，或用 `align-items: start`。
3. 触发条件：在 auto-fit 里给最后一列单独设宽（`:nth-child` 调宽）→ 现象：列数变化时 nth 规则错位 → 修法：改用容器查询或子网格控制特殊行。

边界：本案例对比的是「断点维护成本」与「列数随宽度变化的语义」，两种方案的渲染成本没有可测差异（同一批 8 张卡的布局计算量同级），因此未给出性能对比数值，属无性能差异的方案对比。
