# has 父级选择器

## 1. 现象 / 场景

「子元素的状态要反向影响父级样式」的需求天天有：卡片里有缩略图才开双列，表单里必填项没填完容器要亮红边。用监听器实现要读原始文档对象模型状态、手工比对、再手动改类名，样板代码一大摞还容易漏挂或忘记清理。

复现步骤：

1. 打开案例，切到「JS 监听器（旧）」模式：指标条显示实现这两个行为需要 30 行脚本与 3 个监听器。
2. 取消勾选「带缩略图」→ 卡片退回纵排；清空任一必填输入 → 容器点亮红边。行为正常，但每一步都是脚本在推。
3. 切到「has 选择器（推荐）」模式：监听器个数归零、脚本行数归零，同样的勾选与输入操作，排向与红边照常切换——实际状态由计算样式与 matches 实时核验。

## 2. 原理

`:has()` 是一个把「后代选择器」反过来的函数式伪类：`选择器:has(条件)` 表示存在满足条件的后代（或后续兄弟元素）时命中。它的判定发生在样式计算阶段——浏览器在构建每个元素的匹配树时顺便求值，后代元素的状态（存在与否、伪类翻转）变化会反向传播到祖先的匹配结果，触发祖先与其所在子树重新参与级联。

过去这类需求只能靠脚本，因为传统选择系统只允许「从父看子」，不允许「从子看父」。监听器方案的本质是「用事件模拟样式匹配」：监听每个可能影响状态的元素 → 抄一份匹配逻辑（if 判断）→ 手动把结论写回类名。三个环节各自要维护，字段多了、状态组合多了就会漂移。

`has()` 的代价自然也有：条件可以作用到祖先链，浏览器在部分场景要做的匹配工作量更复杂；但常规「单层父级看子元素」的用法开销与普通后代选择器同量级，可以放心用于交互态样式。

## 3. 方案：关键代码

以 `thumb-card` 与 `form-box` 的样式块（Demo.vue）定位：

```css
/* 场景一：卡片存在缩略图才双列——为什么不用类名切换：
   元素本身的出现/消失已经是「状态源」，.has 的命中会自动跟随 */
.mode-css .thumb-card:has(.thumb) {
  flex-direction: row;
  align-items: center;
}

/* 场景二：容器内存在「必填且仍为空」的输入——为什么用
   :placeholder-shown 而不是 :invalid：空值之外不想把格式错误
   也算进「必填未填」的判定，语义更收紧、更贴合需求 */
.mode-css .form-box:has(input.req:placeholder-shown) {
  border-color: var(--danger);
  background-color: color-mix(in srgb, var(--danger) 6%, var(--surface));
}
```

```ts
// 实时核验：读计算样式而非相信结论（Demo 两种模式共用）
// 1. 为什么读 flexDirection：css 模式的双列由 has 命中产生，
//    读计算样式证明「是样式引擎在生效」而不是 JS 在推
const dir = getComputedStyle(thumbCardRef.value).flexDirection === 'row' ? 'row' : 'column'
// 2. 为什么 js 模式用状态、css 模式用 matches：matches 直接实测
//    has 规则命中情况，等价于「浏览器自己的判定结果」
formBoxRef.value.matches(':has(input.req:placeholder-shown)')
```

## 5. 追问与边界

**Q：has 能监听任意祖先链吗？**
能向后看多级（`div:has(> .item)` 也可以限定直接子级），但要克制：祖链越远，匹配涉及的元素越多，可读性也越差，常规用法是「最近父级看直接后代」。

**Q：它和「父子选择器」提案是同一个东西吗？**
`:has()` 是标准里落地的方案；早年的「父选择器」都停留在设想阶段。现在除了旧 WebView，Chrome / Safari / Firefox 主流版本都已在产品环境可用。

**Q：为什么示例里用 :placeholder-shown 而不是 :invalid？**
`:invalid` 对「required 且为空」与「格式不合法」都会命中，语义太宽；`:placeholder-shown` 精确表达「值仍为空」，和「必填未填」的业务含义一一对应。

**Q：性能上需要注意什么？**
避免把 has 条件挂在高频重排的大容器上、且条件内容复杂的话会放大匹配工作量；交互态（聚焦、悬停）使用常规伪类组合即可，不必层层 has。

踩坑：

1. 触发条件：勾选框用 v-model 渲染缩略图，但忘了行为样式只认 DOM 元素 → 现象：勾选状态变了、布局没变 → 修法：确认缩略图元素真实存在/移除（v-if），has 匹配的是文档，不是响应式变量。
2. 触发条件：把 has 写在会被 scoped 编译的选择器链中段 → 现象：某些选择器片段匹配不到 → 修法：has 条件保留业务语义、外层选择器放到 Demo 根类之下再组合。
3. 触发条件：js 与 css 两种模式同时生效（切换模式忘摘监听器） → 现象：状态被两套机制拉扯 → 修法：统一在 `syncListeners` 里先全量摘除再按需挂载。

边界：本案例属于「行为等价、实现成本对比」型：两种模式产出的视觉效果一致，没有性能差异可测，因此第 4 段用行为与代码指标（行数、监听器个数、实测状态）替代。对照开关适用的前提是浏览器支持 has；目标环境更老时保留监听器方案（见 code 片段的「何时不用」）。
