# 容器查询 @container

## 1. 现象 / 场景

同一张卡片，全宽摆放时好好的，塞进侧栏或弹窗立即挤成一团；写媒体查询补救，可媒体查询只认屏幕宽度，组件摆到宽屏的窄栏里布局依旧僵化。

复现步骤：

1. 打开案例，保持「媒体查询（跟视口）」模式，在桌面宽度下观察：宽容器横排 ✓，固定窄容器（250px）也硬塞横排 ✗。
2. 拖动并排两列中间的分隔条：媒体查询版四处的排向纹丝不动——它跟的是视口，不是容器。
3. 切到「容器查询（推荐）」模式：继续拖动分隔条，宽度跨过 520px 的那列立即从纵排切到横排，「适配场景」实时变成 4/4。

## 2. 原理

`container-type: inline-size` 把声明它的元素注册为一个「查询容器」，同时建立布局包含块：内部元素在样式计算阶段就能按这个容器的实际 inline 尺寸做条件分支。随后内部样式里的 `@container (min-width: 520px)` 不再问视口多宽，而是问「我最近的多层容器祖先多宽」——每个摆位的答案不同，规则逐个求值、互不牵连。

媒体查询的本质是「视口尺寸 → 一批样式规则」的静态映射，写在全局样式层；组件一旦离开开发时的摆放位置，这层映射的前提就塌了。容器查询把判定权下放到组件的宿主容器，正好对应「组件库写组件、页面管布局」的真实分工。

浏览器侧流程：容器宽度在布局阶段确定 → 样式引擎检查容器查询条件 → 命中/未命中的规则进入该容器内部元素的样式树 → 若排向真的变化则触发其内部子树重排。由于 contain 的隔离语义，外层页面不会因为内部切换而整体重算。

## 3. 方案：关键代码

以 `host` / 容器查询块（Demo.vue）定位：

```css
.host {
  /* 1. 为什么先声明 container-type：容器查询的判定对象
        是「最近祖先容器」，没有这一步 @container 永远不命中 */
  container-type: inline-size;
}

@container (min-width: 520px) {
  .cq-card {
    /* 2. 为什么断点是容器宽度：组件的可用空间取决于宿主，
        与视口无关——这正是媒体查询做不到的判定 */
    flex-direction: row;
    align-items: center;
  }
  .cq-card .thumb {
    /* 3. 为什么缩略图要改宽：纵排时它占整行，横排必须收成
        固定宽度让文字吃余下空间——两套尺寸随查询一起切换 */
    width: 96px;
  }
}
```

## 4. 数据对比

| 指标 | 错误（媒体查询版） | 正确（容器查询版） | 测量方式 |
|------|--------------------|--------------------|----------|
| 适配场景数 | 视口 ≥900px 时 2/4（窄容器与窄列错排）；视口 <900px 时恰好接近 4/4 | 恒为 4/4（规则跟每个容器各自求值） | 每个摆位读 `getComputedStyle(卡片).flexDirection`，与「容器宽 ≥520 应横排」的期望逐个比对求和 |
| 参与判定的断点 | 1 条（只跟视口） | 1 条（跟容器，覆盖全部摆位） | 静态统计：两种 CSS 里的查询条数 |
| 容器宽度显示 | 实时 | 实时 | `ResizeObserver` 回调内读 `getBoundingClientRect().width` 回显 |
| 布局切换时机 | 仅当视口宽跨过 900px | 每个容器宽独立跨过 520px 的瞬间 | 拖动分隔条现场观察，排向变化在拖到断点处发生 |

测量说明：

- 指标定义：「适配场景数」指四个摆位（宽容器、窄容器、并排左右两列）中实际排向与期望排向一致的个数，取值 0~4；「断点数」为样式层面参与判定的查询规则条数（静态值）。
- 采集方式：`ResizeObserver` 监听四个摆位容器；排向一律读计算样式 `flexDirection`，不靠猜测规则；`window.innerWidth` 同步视口宽度。
- 数据规模：同一张卡片 ×4 个摆位，分隔条在 22%~78% 区间拖动。
- 环境：Chrome / Edge 近两年版本（需支持 container queries），桌面与移动窗口均可复现。
- 取样：适配数为状态判定（每次拖动后即时重算），非时间采样；拖到断点两侧各一次即可完整复现 0→4 与 4→0 的变化。
- 以 Demo 面板实测为准；本案例无时间类性能数值。

## 5. 追问与边界

**Q：容器查询单位和 vw 有什么不同？**
`cqw / cqh / cqi` 等单位基于最近容器的尺寸求值，放在组件内部就是「容器宽的 1%」；vw 永远是视口。做组件内流式排版用 cqi，整页级别才用 vw。

**Q：container-type: inline-size 会不会影响容器自身布局？**
会。它附带 containment 语义：容器自身的块尺寸不受内容影响（inline 尺寸仍然正常），所以给不高度自适应的外层做容器要留心——自高度以内容为准的嵌套常见坑见下。

**Q：为什么不用 ResizeObserver + 手动切 class 的老方案？**
老方案把样式逻辑搬进 JS：监听、防抖、卸载清理都要自己管，且首帧前会闪一下默认样式。容器查询把这套收编进样式引擎，JS 一行不用写。

**Q：媒体查询版在小屏（<900px）适配数也是 4/4，是不是说明它也够用？**
小屏恰好「视口窄=容器窄」，静态映射碰巧对上；一旦组件被放进真实页面的任意栏位（这正是组件库的常态），映射前提就塌了。对照组的意义就是展示这种「摆错位置就失效」的脆弱性。

踩坑：

1. 触发条件：把 `container-type: inline-size` 加在需要以内容撑高的元素上 → 现象：容器自身高度塌陷（inline-size 容器的高度不再由内容撑开） → 修法：包一层外层提供尺寸，或在专门的宿主元素上声明。
2. 触发条件：写成容器内找不到最近容器 → 现象：`@container` 规则永不命中 → 修法：检查祖先链上是否真的有 container-type，或显式用命名容器 `container-name`。
3. 触发条件：容器内大量元素各自查询 → 现象：拖动时样式重算偏多 → 修法：查询规则收敛到容器级 class，让级联继承下去。

边界：本案例对比的是「适配的正确性」而非性能——两种方案的渲染开销同级，没有可测的性能差异，因此第 4 段只用行为指标（适配场景数、断点数、排向切换时机）。对照开关的意义在于展示判定对象（视口 vs 容器）的根本差异。
