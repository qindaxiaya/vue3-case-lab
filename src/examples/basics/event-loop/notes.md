# 宏任务与微任务执行顺序

## 1. 现象 / 场景

一句话：定时器、Promise、逐帧回调混在一起时，输出顺序和脑补的「先同步后异步」完全对不上。

复现：

1. 打开案例，先看「直觉预期」里的脑补顺序（定时器先于微任务）。
2. 切到「真实输出」，点「运行」，对照每行的时间戳与类型徽章。
3. 打开「慢任务」（主线程忙 200ms）再运行一次，微任务依然插在定时器前面。

## 2. 原理

事件循环一轮的骨架：取一个宏任务（点击回调、定时器）执行 → 执行期间排入的同步代码跑完 → **立刻清空整个微任务队列**（Promise.then、queueMicrotask）→ 如果浏览器判断该渲染了，先跑逐帧回调再绘制 → 回到开头取下一个宏任务。

所以「微任务」不是排所有代码最后，而是插在「上一个宏任务刚结束、下一个宏任务还没开始」的缝隙里；「先同步后异步」直觉把微任务当成了普通异步任务，把它排到了定时器后面。setTimeout 有约 1ms 的最小延迟且受嵌套层级限制，无论如何也抢不过微任务。

## 3. 方案：关键代码

```ts
function run(): void {
  origin.value = performance.now()
  push('macro-click', '用户点击回调（本次运行起点）') // 1. 当前宏任务本体，拿它当地面上一条时间线

  setTimeout(() => push('macro-timer', 'setTimeout 0ms 的回调'), 0)
  Promise.resolve().then(() => push('micro-then', 'Promise.then 微任务'))
  queueMicrotask(() => push('micro-qm', 'queueMicrotask 微任务'))
  // 2. 同一次点击里把五类任务一次排入，才能公平比较顺序，而不是各测各的

  requestAnimationFrame(() => push('frame-raf', '渲染一帧前的逐帧回调'))
  setTimeout(() => push('macro-timer', 'setTimeout 200ms 的回调'), 200)

  if (slowTask.value) busyWait(200) // 3. 慢任务放在排程之后：证明它只拖住当前宏任务
  setTimeout(() => { summary.value = '...' }, 300) // 等队列走完再总结，避免抢跑
}
```

测量说明：

- 环境：Chrome / Edge 现代版本，桌面端，未开 CPU 节流；rAF 与 setTimeout 0ms 的相对位置逐机略有差异，**以 Demo 面板实测的时间戳为准**。
- 取样：每点一次「运行」为一次完整测量；时间戳取相对起点。
- 行数 / 位数（微任务第 2、3 位）是 Demo 日志里数得出来的，与浏览器实现一致。

## 5. 追问与边界

**Q：微任务里再排微任务会怎样？**
当前宏任务结束后队列会一直清，微任务生微任务会让本轮循环「清不完」，页面卡住——不要在同一轮里无限 then 接 then。

**Q：setTimeout(fn, 0) 为什么不是 0ms？**
嵌套层级 ≥5 后最小间隔被压到约 4ms，加上排程开销，实测通常 1~5ms；这个细节不如「微任务先于它」重要。

**Q：什么时候用 rAF，什么时候用 setTimeout？**
要和绘制同频（进度条、跟随动画）用逐帧回调；只是「晚点再跑」的修补逻辑才用定时器。

踩坑：

1. 微任务里自己再生微任务 → 页面假死 → 加深度/次数上限。
2. 把密集计算写在 Promise.then 里以为「不阻塞」 → 依然阻塞 → 拆定时器切片。
3. 用 setTimeout 硬凑动画 → 与绘制不同频丢帧 → 换逐帧回调。

边界：本案例演示的是浏览器事件循环；Node.js 有自己的循环细节（如阶段划分），以浏览器为准。直觉预期序列只是静态展示——它本来就无法在浏览器里按脑补顺序跑出来，这正是对照开关的价值。
