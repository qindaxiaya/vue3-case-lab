# structuredClone 深拷贝与类型保真

## 1. 现象 / 场景

一句话：用 `JSON.parse(JSON.stringify)` 存一份数据快照，日期全部变字符串、集合字段直接丢空，耗时还比原生深拷贝慢。

复现：

1. 打开案例，点「重测三种方法」，观察每个方法的耗时中位数与「真日期副本」条数。
2. 对照下方支持类型表：JSON 往返五项全挂，展开法只有点过名字段的日期与映射通过。
3. 切到 100000 条再重测，耗时差距随数据规模放大。

## 2. 原理

JSON 字符串往返只认识字符串、数字、布尔这些基础类型：日期被序列化成 ISO 字符串（`instanceof Date` 为否，操作时容易炸）；映射/集合序列化后变空对象；正则变 `{}`；循环引用在序列化时直接抛错。它是「字符串语义」的拷贝，不是「类型语义」的拷贝。

`structuredClone` 是浏览器原生的结构化克隆算法（与给另一端发数据用的是同一套），按真实类型克隆：日期仍是日期、映射仍是映射（键值集合），互相引用的对象在副本里依旧互相引用且不会绕死。代价是不能克隆函数与回调相关的引用——但这本来也属于深拷贝的合理边界。

「展开 + 手动点名」是折中：必须为每一种嵌套类型写一行转换代码，漏写的字段会共享原引用（改副本就把原数据改了）——加一种字段就要同步补一处代码，维护成本与字段数线性相关。

## 3. 方案：关键代码

```ts
// 为什么先留 CopyFn 签名：三种方法接入同一份测试数据同一套计时口径
type CopyFn = (items: Item[]) => unknown

const copyStructured: CopyFn = (items) => structuredClone(items)
// 1. 为什么用 structuredClone 而不是 JSON：类型按原样克隆，连循环引用都不抛错

const copyJson: CopyFn = (items) => JSON.parse(JSON.stringify(items)) as unknown
// 2. 为什么标 as unknown：它返回的内容类型已经「不保真」，提示引用方先验类型

const copySpread: CopyFn = (items) =>
  items.map((it) => ({
    ...it,
    createdAt: new Date(it.createdAt.getTime()),
    tags: [...it.tags],
    meta: new Map(it.meta), // 3. 为什么逐字段点名：不做一行就共享原引用，改副本会污染原数据
  }))
```

## 4. 数据对比

| 指标 | JSON 往返 | 展开点名 | structuredClone | 测量方式 |
|------|-----------|----------|-----------------|----------|
| 10000/100000 条耗时中位数 | 见面板 | 见面板 | 见面板 | `performance.now()` 包住单次拷贝 |
| 「真日期副本」条数 | 0（全变字符串） | =总条数（点过名） | =总条数 | 对副本逐条 `instanceof Date` 计数 |

测量说明：

- 环境：现代 Chrome / Edge 桌面端，未开 CPU 节流；数据每次按固定规则重建（id 连续、字段取模），保证可复现。
- 数据规模：一万或十万条，每条含日期、两个元素的映射与两项标签数组。
- 取样：同数据连跑 3 轮取中位数，面板显示每方法三次的中位数毫秒值；数值区间在不同机型差异较大，以 Demo 面板实测为准。
- 支持类型判定不随数据规模变化（小样本固定结论），重测页面时会自动跑一遍。

## 5. 追问与边界

**Q：structuredClone 比 JSON 往返一定快吗？**
小数据两极差异不可见；本案例实测区间在大数据规模下 structuredClone 通常更快（JSON 要在字符串上折返两趟），具体倍数以面板为准。

**Q：Vue 的响应式对象能直接 structuredClone 吗？**
不建议。reactive 数据是一层 Proxy，克隆走的是普通对象路径：条目会丢、结构会奇怪；应先用 toRaw / 手动平铺转成原始结构再克隆。

**Q：什么时候还需要 Lodash.cloneDeep 这类库？**
需要兼容旧浏览器、或数据里混着「不可克隆的类型但可被库特判」的场景；现代浏览器里结构化克隆已覆盖绝大多数情况。

踩坑：

1. JSON 往返把日期变字符串后又当日期用 → 运行时炸 → 深拷贝用 structuredClone。
2. 「展开」里漏写一个嵌套字段 → 改副本污染原数据 → 每加字段同步补点名。
3. 想克隆含函数回调的配置对象 → 谁都克隆不了 → 只拷数据字段。

边界：本案例不涉及跨进程传递（那是同样的算法但走另一条通道）；「错误 / 正确」对照通过三方法支持类型表与保真计数体现；展开法的「失败」特指漏点名字段共享引用，若全部点名到位则等价于深拷贝但代码更多。
