# 抽屉侧滑与退出动画

## 1. 现象 / 场景

点关闭，抽屉和遮罩在同一瞬间消失，没有任何退场过程；如果打开动画刚做到一半就关闭，还能看到面板停在半路突然被抹掉。用户不知道刚才那个面板是往哪边收的，下一次打开也会觉得突兀。

复现步骤：

1. 打开案例，保持默认的「直接卸载（旧）」，点「打开抽屉」，再点右上角关闭：面板与遮罩立刻消失，「关闭后仍在文档中的帧数」不增长。
2. 切到「等动画结束（推荐）」，重复打开与关闭：面板向右滑出、遮罩逐渐变透明，帧数持续累加，过渡结束事件计数加 1，节点随后才被移除。
3. 打开抽屉后试三件事：按 Esc、点遮罩、点「关闭」按钮，三种方式都要能关闭，并且焦点回到「打开抽屉」。
4. 抽屉打开时滚动背景页面，滚动被锁住；关闭后恢复。
5. 点「模拟减少动态效果」再开关一次：过渡被跳过、节点立刻移除，这是真实项目在系统开启该设置时该走的分支。系统真的开启该设置时，面板顶部会出现一行提示，本案例仍然播放动画，方便你对比两种关闭方式。

## 2. 原理

进场动画通常靠「节点先挂载，再在下一帧加打开类」触发：初始样式是屏外位置，打开类是屏内位置，两个值不同，浏览器就会在两者之间补中间帧。退场刚好相反：把打开类去掉，节点从屏内回到屏外，浏览器开始补帧。

但节点的删除不参与这个过程。只要从文档里移除，浏览器在下一帧就画不出它了，透明度和位移都无从谈起。所以退场必须拆成两步：先改状态让样式过渡跑起来，等过渡结束再把节点删掉。否则看到的永远是「啪」地消失。

`transitionend` 事件就是「这一段过渡真的跑完了」的信号，它在过渡属性到达终点后触发，事件对象里带 `propertyName`，可以知道是哪条属性结束。面板的位移与遮罩的透明度是两条独立的过渡，选一条作为卸载信号即可；本案例等面板的 `transform` 结束。

这个事件会从子元素冒泡上来：面板里任何元素只要也有过渡，父级监听器都会收到。因此必须同时判断 `event.target === event.currentTarget` 和 `event.propertyName`，否则可能在子元素的过渡结束时提前卸载。

还要考虑事件不来的情况：系统开启「减少动态效果」后过渡被压到极短，或者标签页在后台被浏览器节流，事件可能延迟甚至不到。所以代码里要留兜底计时器，并在卸载、切换模式时统一清掉。

## 3. 方案：关键代码

以 `requestClose`、`onPanelTransitionEnd`、`finalizeClose`（Demo.vue）定位：

```ts
/** 是否跳过过渡：旧做法，或手动模拟「系统开启减少动态效果」 */
const instant = computed(() => mode.value === 'unmount' || mockReduce.value)

function requestClose(): void {
  if (!visible.value || closing.value) return
  closing.value = true
  cancelOpenFrames()

  if (instant.value) {
    startFrameWatch()
    void nextTick(() => finalizeClose())
    return
  }

  // 为什么先只改状态：节点留在文档里，位移与透明度才有时间过渡
  shown.value = false
  startFrameWatch()

  // 为什么留兜底：过渡结束事件可能因后台节流而迟到或不到
  fallbackTimer = window.setTimeout(() => finalizeClose(), 600)
}

function onPanelTransitionEnd(event: TransitionEvent): void {
  // 为什么双重过滤：子元素过渡会冒泡，且面板可能有多条过渡属性
  if (event.target !== event.currentTarget) return
  if (event.propertyName !== 'transform') return
  transitionEnds.value++
  if (closing.value) finalizeClose()
}

function finalizeClose(): void {
  if (!visible.value) return
  window.clearTimeout(fallbackTimer)
  stopFrameWatch()
  visible.value = false
  // 为什么在这里才还原：卸载是最后一步，滚动锁与监听都要一起收尾
  unlockScroll()
  document.removeEventListener('keydown', onKeydown)
  triggerRef.value?.focus()
}
```

## 4. 数据对比

| 指标 | 直接卸载（旧） | 等动画结束（新） | 测量方式 |
|------|----------------|------------------|----------|
| 关闭后节点仍在文档中的帧数 | 不增长（样式无过渡，卸载早于下一次绘制） | 过渡期间持续增长 | 每帧检查面板节点是否仍在文档中，在就加 1，可点重置后复测 |
| 面板过渡结束事件 | 0 次 | 每次打开、关闭各 1 次 | 面板上的事件监听器计数 |
| 退场是否可见 | 面板与遮罩瞬间消失 | 面板滑出 + 遮罩淡出 | 目视 + 帧计数 |
| 节点移除时机 | 关闭调用后的下一次渲染 | 过渡结束事件到达之后 | 面板状态文案与帧计数 |
| 打开时的滚动锁 | 有 | 有 | 打开后滚背景页面 |
| 关闭后的焦点 | 回到触发按钮 | 回到触发按钮 | 用 Tab 检查焦点位置 |

测量说明：

- 指标定义：「帧数」指从点击关闭开始，到面板节点离开文档为止，浏览器每绘制一帧就加 1；「过渡结束事件」指面板自身 `transform` 的 `transitionend` 次数。
- 采集方式：帧数用逐帧循环读取节点的「是否仍在文档中」，事件用监听器累加；两者都在 Demo 面板实时显示。
- 数据规模：一个抽屉，5 条消息，遮罩与面板各一条过渡。
- 环境：需要支持固定定位与过渡的现代浏览器；后台标签页会节流逐帧回调，测出的帧数不代表前台节奏，应把页面切到前台再测。
- 取样：点「重置」清零后重复关闭 3 次；旧模式每次都不增长，新模式每次都会增长。
- 本案例不写死具体帧数或时长，因为帧数受刷新率与后台节流影响；只比较「会不会进入下一帧」这一可核对的事实。

## 5. 追问与边界

**Q：为什么不等遮罩的透明度过渡结束再卸载？**
两条过渡同时开始，谁先结束取决于各自时长；选一条稳定、明确的属性作为信号就够了。等两条都结束需要计数或 `Promise.all` 一类协调，反而更容易漏事件。本案例只面板有 `transform`，选它最直接。

**Q：为什么不直接用 Vue 的内置过渡组件？**
内置过渡组件能处理进出场，但「等事件再卸载」背后的机制仍然一样；理解 `transitionend` 与节点生命周期后，用内置组件会更省事。这个案例用原生事件是为了把时机与证据显式展示出来。

**Q：系统开启「减少动态效果」后还要等过渡吗？**
不要。过渡被压到极短时继续等事件只会让关闭感觉迟钝；真实项目应当在检测到该设置时直接跳过动画、立刻卸载，保留功能而不强迫用户看动画。

这个案例的特殊之处在于「动画就是教学内容」：如果严格跟随系统设置，两种关闭方式会长得完全一样，案例就白看了。所以 Demo 把系统设置降级成两条辅助信息——顶部提示当前检测到的设置，面板上提供「模拟减少动态效果」开关来展示跳过分支——而演示本身仍然播放过渡。真实业务代码不要照抄这个取舍，按上一段直接跳过即可。

**Q：关闭后为什么一定要把焦点还给触发按钮？**
键盘用户关闭抽屉后，焦点如果留在已被移除的节点上，会掉回页面顶部，下一次 Tab 从哪里开始完全不可预期。归还焦点是对话框类组件的基本要求。

踩坑：

1. 触发条件：在文档上监听 `transitionend` 且不过滤目标 → 现象：抽屉里某个子元素的过渡一结束就提前卸载 → 修法：判断事件目标等于当前元素，并核对属性名。
2. 触发条件：滚动锁直接写 `document.body.style.overflow = ''` → 现象：页面原本的滚动设置被覆盖，关闭后行为不对 → 修法：打开前保存原值，关闭时还原。
3. 触发条件：节点刚挂载就加打开类 → 现象：浏览器把初始位移和打开类合并成一次样式计算，没有过渡 → 修法：先等一帧让初始样式生效，再加打开类。

边界：如果抽屉需要支持手势拖拽关闭，位移会由拖拽实时控制，退场信号要改成「松手后的目标位置」而不是单纯等事件；如果面板内有视频、画布等持续渲染的内容，退场期间仍会占用资源，应在开始关闭时就暂停。滚动锁与焦点归还在嵌套弹层（抽屉里再开弹窗）时需要按栈管理，不能各自直接覆盖页面状态。
