# 折叠面板平滑展开

## 1. 现象 / 场景

问答面板点开时要么「啪」地出现，要么用了 `max-height` 之后展开怪怪的：短内容很快到底、后面一段动画什么也没发生；长内容又被裁掉半截。换成脚本量高度能解决动画，但每开一次都要读一次内容高度，内容一变长，之前写下的像素值就过期。

复现步骤：

1. 打开案例，默认是「脚本量高（旧）」：依次展开三条问答，面板上的「读取 scrollHeight」每次加 1，最近写入里出现一个像素值。
2. 切到「grid 过渡（推荐）」：任意展开、收起，读取次数始终是 0，但动画照样平滑。
3. 对比两条长短差别很大的答案：旧方案每次都要脚本先量出终点；新方案的展开时长固定，不随内容长度变化。
4. 点「重置（全部收起）」可随时回到初始状态，再测一轮。

## 2. 原理

`height` 从 `0` 过渡到 `auto` 不会产生动画。过渡需要在两个「可以计算的数值」之间插值，而 `auto` 的终点要等内容排版完成才知道，浏览器在动画开始前拿不到它，只能直接切换。这是规范层面的限制，不是写法问题。

旧方案绕开的办法是「先量后写」：把面板高度设为 0、保留 `overflow: hidden`，此时 `scrollHeight` 仍能读到内容完整高度；把这个像素值写进行内 `height`，浏览器就有了明确的终点，过渡可以正常跑。收起时再把行内高度写回 0。代价是每打开一条都要读一次 `scrollHeight`，而读它会强制浏览器先结算布局；内容、字体、图片变化后还要重新量。

网格方案把「高度」换成「行高比例」：面板是 1 行 1 列的网格，`grid-template-rows: 0fr` 与 `1fr` 都是可插值的比例，终点由网格根据内容自己算。浏览器在过渡时只需要在 0 到 1 之间分配剩余空间，不需要脚本提供像素值。

要让网格行真的能收缩到 0，内层必须有 `min-height: 0` 和 `overflow: hidden`。网格项的默认最小尺寸是「内容尺寸」，不写 `min-height: 0` 时，内容会把 0fr 的行撑开，收起就失效。内边距也要放在更内层：如果把 padding 放在负责裁切的元素上，即使高度是 0，padding 仍会占出一段空白。

## 3. 方案：关键代码

以 `toggle` 与 `.grid-panel`（Demo.vue）定位：

```ts
function toggle(id: string): void {
  const isOpen = openId.value === id

  if (mode.value === 'grid') {
    // 为什么只改状态：行高过渡由样式完成，脚本不参与计算
    openId.value = isOpen ? null : id
    return
  }

  if (openId.value) heights[openId.value] = 0
  if (isOpen) {
    heights[id] = 0
    openId.value = null
    return
  }

  // 为什么先读再加 1：这条读取就是旧方案每次展开的固定成本
  measureReads.value++
  const contentHeight = getPanel(id)?.scrollHeight ?? 0
  // 为什么写像素而不写 auto：auto 不能参与过渡
  heights[id] = contentHeight
  openId.value = id
}
```

```css
.grid-panel {
  /* 为什么用行比例：0fr 和 1fr 都能插值，终点由网格按内容算 */
  display: grid;
  grid-template-rows: 0fr;
  transition: grid-template-rows 0.32s var(--ease-out);
}

.grid-panel.open {
  grid-template-rows: 1fr;
}

/* 为什么内层要 min-height: 0：不写的话内容会把 0fr 的行撑开 */
.grid-panel > .answer-wrap {
  min-height: 0;
  overflow: hidden;
}

/* 为什么 padding 放在更内层：放在裁切层会让收起的面板仍留一条空白 */
.faq-answer {
  padding: 0 0.9rem 0.85rem 2.95rem;
}
```

## 4. 数据对比

| 指标 | 脚本量高（旧） | grid 过渡（新） | 测量方式 |
|------|----------------|------------------|----------|
| 每次展开读取 `scrollHeight` | 1 次 | 0 次 | Demo 面板计数器，每点开一条加 1，可先重置再数 |
| 开关逻辑中与高度有关的代码 | 7 行（读高度、写行内值、收起归零、记录） | 0 行 | 直接数 `toggle` 里处理高度的语句 |
| 维护的行内高度状态 | 每个打开项 1 个像素值 | 0 个 | 检查面板的 `style` 属性 |
| 内容变长后的结果 | 旧值过期，需要重新量 | 不影响 | 修改答案文字后再展开对比 |
| 需要 JS 测量高度的行数 | 1 行/次 | 0 行 | 面板指标直接显示 |

测量说明：

- 指标定义：「读取次数」指用户每展开一条问答，脚本调用 `scrollHeight` 的次数；「与高度有关的代码」指开关函数里读、写、清零高度的语句。
- 采集方式：Demo 内计数器累加，点击「重置」清零；行内高度可直接在开发者工具里查看。
- 数据规模：3 条问答，答案段落数分别为 2、4、2，长度差异明显。
- 环境：桌面与手机视口均可；两种方案的展开时长都写死为同一个过渡时长，比较的是脚本成本而不是速度。
- 取样：重置后连续展开三条为一轮，可重复多轮，计数结果与操作次数一致。
- 本案例不宣称性能差异：没有测帧率或耗时，比较的是「要不要脚本量高度」这件可核对的事。

## 5. 追问与边界

**Q：为什么不用 `max-height: 9999px`？**
固定上限会让实际内容高度只占过渡的一小段：0 到 9999 的动画里，内容可能在前十分之一就长完了，剩下时间什么也看不到，看起来像瞬间展开；收起时又要先等一大段「看不见的高度」缩完，才轮到你真正看到内容动。上限越保守，长内容越容易被裁切。

**Q：grid 行高过渡的兼容性如何？**
现代浏览器已经支持 `fr` 单位之间的过渡，但老版本可能直接跳到终点。需要兼容时，回到「量高度写行内值」的方案，并把重新测量挂在内容变化、容器宽度变化之后；不要指望一次测量永久有效。

**Q：折叠面板的无障碍要注意什么？**
触发按钮要有 `aria-expanded` 和 `aria-controls`，面板本体标 `role="region"` 并用 `aria-labelledby` 指回按钮；收起时最好同时加 `aria-hidden`，避免读屏软件读到看不见的内容。如果面板里有链接或按钮，还要保证收起状态下它们不能被 Tab 聚焦。

**Q：答案里有图片，图片晚到会怎样？**
网格行会根据最终内容高度自动调整，图片加载完成后展开状态仍然正确；旧方案量到的值可能偏小，需要监听图片加载完成或容器尺寸变化后重新测量，否则内容会被裁掉。

踩坑：

1. 触发条件：网格内层忘记 `min-height: 0` → 现象：收起后仍留一条高度，0fr 不生效 → 修法：给直接子元素补 `min-height: 0` 与 `overflow: hidden`。
2. 触发条件：把 padding 写在负责裁切的子元素上 → 现象：收起了但还露出 padding 的空白 → 修法：padding 放到更内层的内容块。
3. 触发条件：旧方案用 `display: none` 收起 → 现象：`scrollHeight` 读到 0，展开没有动画 → 修法：用 `height: 0` 加 `overflow: hidden`，保持节点参与测量。

边界：本方案适合单层、内容高度由排版决定的折叠面板；如果面板里还要做横向滑动、虚拟滚动或嵌套折叠，需要单独处理每层的裁切与焦点。对老浏览器有硬性要求时，脚本量高仍是可靠退路，但要接受每次展开的布局读取成本。
