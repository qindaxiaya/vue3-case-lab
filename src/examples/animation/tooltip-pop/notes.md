# 提示气泡：延迟出现与定位

## 1. 现象 / 场景

给图标按钮加提示，最省事的做法是写一个 `title` 属性。上线后发现：提示条样式跟站点完全不搭、圆角和配色改不了；鼠标停多久才出现完全看浏览器心情；手机上点一下按钮，提示根本不出现。产品再要求「延迟 0.2 秒出现、深色气泡、带小三角」，`title` 就彻底做不到了。

复现步骤：

1. 打开案例，默认是「原生 title（旧）」：鼠标停在按钮上，等浏览器自己的提示条出现；换到手机模拟器点一下，看不到提示。
2. 切到「自建气泡（推荐）」：鼠标移入后先不出现，等待期间面板的「延迟计时器」显示等待中，约 180ms 后气泡出现，面板显示本次实际用时。
3. 鼠标移出按钮：气泡立即消失，不保留渐隐期。
4. 用 Tab 键聚焦按钮：气泡立即出现，触发来源显示「键盘」；按 Tab 离开或点页面其他位置，气泡立即收起。
5. 把窗口缩到 375px：气泡改到按钮下方，不会顶出视口。
6. 点「模拟减少动态效果」：开关变成「模拟中：已降级」，再移入按钮，气泡不再淡入位移、直接出现；延迟时机仍然保留，因为它属于「什么时候出现」而不是动画。

## 2. 原理

`title` 是浏览器提供的「原生提示」，页面元素上只是一个字符串。浏览器在内部决定什么时候显示、显示多久、用什么字体与配色、是否换行，这些都不进入页面的样式系统；脚本也读不到「提示正在显示」这个状态。不同浏览器、不同平台的表现还不一样，触摸设备上通常没有悬停，提示基本不会出现。它适合做「最后兜底的一句话说明」，不适合承载设计稿里的提示条。

自建气泡的本质是「一个绝对定位的元素 + 一个定时器 + 一组事件」。外层容器写 `position: relative`，气泡写 `position: absolute`，`bottom: calc(100% + 间隙)` 让它贴在触发器上方，`left: 50%` 加 `translateX(-50%)` 让它水平居中；小三角用伪元素或独立方块旋转 45 度，贴着气泡底边。绝对定位的元素不占文档流，不会把周围内容挤开。

出现时机由定时器控制：指针进入时记录当前时刻并 `setTimeout`，延迟到了再显示；指针离开时立刻清掉定时器并隐藏，所以「快速划过」不会闪出一堆气泡。键盘聚焦要单独处理：鼠标悬停是「有意的停留」，可以等；Tab 聚焦是「已经选中了它」，等 180ms 只会让人觉得卡，所以聚焦立即显示。两条路径都写入同一个「显示」函数，状态与面板读数才能对得上。

隐藏时同时要做三件事：清掉定时器（避免延迟到了又弹出来）、把透明度与可见性切回隐藏（保留过渡的空间）、把 `aria-hidden` 设为真（否则读屏软件仍会念出看不见的说明）。`role="tooltip"` 告诉辅助技术这是说明性内容，触发器上的 `aria-describedby` 把两者关联起来；气泡显示时才让关联生效，隐藏时由 `aria-hidden` 兜住。

定位要选「相对触发器」，而不是相对页面。触发器可能出现在列表里、弹窗里，页面滚动或布局变化时，相对定位会自动跟着走，不需要脚本监听滚动重算坐标。代价是父级不能有 `overflow: hidden`，否则气泡会被裁掉；本案例的演示区显式保持溢出可见。窄屏还要考虑视口边界：上方空间不够时改到下方，是成本最低的适配。

气泡的淡入与位移属于装饰动画：系统开启「减少动态效果」时，真实项目应当据此降级，只保留「出现 / 消失」这个状态变化，延迟与显隐时机不受影响。本案例为了让淡入看得见，演示默认仍然播放；点「模拟减少动态效果」可以查看降级后的样子。

## 3. 方案：关键代码

以 `scheduleShow`、`onPointerEnter`、`.tip-bubble`（Demo.vue）定位：

```ts
const SHOW_DELAY = 180
let showTimer = 0
let armedAt = 0

function scheduleShow(from: '鼠标' | '键盘'): void {
  clearShowTimer()
  if (mode.value !== 'custom') return

  if (from === '键盘') {
    // 为什么键盘不等：Tab 已经选中了元素，再等只会显得卡
    showNow('键盘')
    return
  }

  armedAt = performance.now()
  pending.value = true
  // 为什么延迟：指针只是路过时不该弹气泡
  showTimer = window.setTimeout(() => {
    showTimer = 0
    pending.value = false
    showNow('鼠标')
  }, SHOW_DELAY)
}

function onPointerEnter(event: PointerEvent): void {
  // 为什么先看指针类型：手指没有悬停，按住就弹气泡会挡住操作
  if (event.pointerType !== 'mouse') {
    touchSkipped.value++
    return
  }
  scheduleShow('鼠标')
}

onUnmounted(() => {
  // 为什么必须清定时器：卸载后回调仍会改已经销毁的状态
  clearShowTimer()
})
```

```css
.tip-wrap {
  /* 为什么相对定位：气泡跟着触发器走，滚动与布局变化都不用脚本重算 */
  position: relative;
  display: inline-flex;
}

.tip-bubble {
  position: absolute;
  bottom: calc(100% + 12px);
  left: 50%;
  /* 为什么用 translate 居中：不用知道气泡自身宽度 */
  transform: translate(-50%, 4px);
  opacity: 0;
  visibility: hidden;
  pointer-events: none;
  transition: opacity var(--transition), transform var(--transition);
}

.tip-bubble.show {
  opacity: 1;
  visibility: visible;
  transform: translate(-50%, 0);
}
```

## 4. 数据对比

| 指标 | 原生 title（旧） | 自建气泡（新） | 测量方式 |
|------|------------------|----------------|----------|
| 出现延迟是否可配 | 否，由浏览器决定 | 是，鼠标 180ms | Demo 面板「配置延迟」 |
| 页面能读到的显示状态 | 无 | 显示中 / 等待中 / 未显示 | Demo 面板「状态」 |
| 键盘聚焦是否出现 | 通常不出现 | 立即出现 | 用 Tab 键试 |
| 触摸设备表现 | 基本不出现 | 跳过指针触发的次数可核对 | Demo 面板「触摸跳过」 |
| 气泡样式声明条数 | 0 条（页面改不了） | 19 条基础声明 + 3 条显示态声明 | 数 `.tip-bubble` 与 `.tip-bubble.show` |
| 事件监听器个数 | 0 个（浏览器内部处理） | 4 个（进入 / 离开 / 聚焦 / 失焦） | 数模板上的事件绑定 |
| 需要自己清理的定时器 | 0 个 | 1 个 | 数脚本里的 `setTimeout` |

测量说明：

- 指标定义：「配置延迟」是鼠标悬停到气泡出现的等待时间；「本次用时」是从触发到真正显示的实际耗时，用 `performance.now()` 记录起点，在显示函数里相减。
- 采集方式：Demo 面板直接显示状态、来源与用时；样式声明条数可以在源码里逐条数，不依赖开发者工具。
- 数据规模：一个触发器、一段说明文案；不涉及列表虚拟化或批量渲染。
- 环境：桌面鼠标、键盘各走一遍；375px 视口检查气泡是否改到下方且页面无横向溢出。
- 取样：鼠标移入后等气泡出现、移出、再移入，重复几次看「本次用时」是否围绕配置值波动；不要把它当成性能指标。
- 本案例不宣称性能差异：比较的是「延迟与样式能不能控制」「键盘与触摸是否可用」，没有测渲染耗时。

## 5. 追问与边界（面试高频）

**Q：什么时候可以继续用原生 `title`？**
只在「补充说明、可有可无、样式不重要」的场景用，比如纯文字链接的补充解释。只要提示要贴合设计、要在键盘操作时出现、要控制延迟，就该自建。也可以两者并存：`title` 作为兜底，自建气泡作为主体验，但要注意别让用户同时看到两条提示。

**Q：为什么鼠标要延迟，键盘却立即显示？**
鼠标移动是连续的，指针路过按钮时立刻弹提示会一直闪；延迟一下能过滤掉「只是路过」。键盘聚焦是一次明确的选择，用户已经停在按钮上了，再等只会增加操作成本。这不是技术限制，而是两种输入方式的意图不同。

**Q：`aria-describedby` 和 `aria-label` 有什么区别？**
`aria-label` 会替代元素原本的可读名称，适合图标按钮这种没有文字的元素；`aria-describedby` 是补充说明，读屏会先读名称再读描述。气泡是解释性内容，用 `aria-describedby` 更合适；如果触发器本身没有文字，两个都要补。

**Q：气泡总是被父容器裁掉怎么办？**
先检查父级链上的 `overflow: hidden`，能放开就放开；不能放开时，把气泡渲染到页面根节点（传送门思路），再用触发器矩形算位置。代价是要监听滚动与尺寸变化来更新坐标，复杂度明显上升，所以优先选「换一个不裁切的父级」。

**Q：气泡贴到视口边缘怎么办？**
简单做法是按断点切换上下位置（本案例窄屏改到下方）；更完整的做法是量触发器与视口的距离，空间不够就翻到另一侧，并限制最大宽度。真正做成组件时，还要处理翻转后的箭头位置与动画方向。

**Q：系统开启了「减少动态效果」，气泡还弹吗？**
弹，但真实项目应当据此降级：去掉淡入与位移，让气泡直接出现。延迟、显隐时机、`aria-hidden` 这些是功能性的，不能跟着砍——它们决定「什么时候出现、读屏能不能念到」。本案例为了方便观察淡入，演示默认仍然播放，点「模拟减少动态效果」可以切到降级分支；降级后你会发现延迟依然生效，只是没有过渡帧。

踩坑：

1. 触发条件：父容器写了 `overflow: hidden` → 现象：气泡只露出半截或完全看不到 → 修法：让演示区保持溢出可见，或把气泡挂到页面根节点再定位。
2. 触发条件：隐藏时只改透明度，不改 `aria-hidden` → 现象：视觉上没显示，读屏却把说明念出来 → 修法：显隐状态与 `aria-hidden` 用同一个布尔值驱动。
3. 触发条件：组件卸载时不清延迟定时器 → 现象：切换路由后定时器到点，控制台报状态更新错误或出现幽灵提示 → 修法：在卸载钩子里清掉定时器并把等待状态复位。

边界：自建气泡适合一到两行短说明，不适合放按钮、链接等可交互内容（气泡里能点的东西很难用键盘到达）。触发器在滚动容器里时，相对定位会跟着滚，这是优点；但如果父级裁切无法避免，就要考虑传送到页面根节点。原生 `title` 在触摸设备上不可靠，不要把关键信息只放在提示里。
