# 乐观更新与回滚

## 1. 现象 / 场景

点赞按钮点下去没反应，用户以为没点到，又连点几下；等接口回来，计数一下跳好几格，或者弹出一串失败提示。网络越差，这种「点了没反应」的体感越明显。

复现步骤：

1. 切到「乐观更新（推荐）」，点第一条动态的爱心，界面立刻变红、计数 +1。
2. 点亮「模拟接口失败」再点赞，观察 300ms 后爱心和计数自动退回，并出现失败提示。
3. 切到「等响应再改」，重复点赞，对比提交期间界面完全不动。

## 2. 原理

默认的「悲观」写法是：发请求 → 等成功 → 改本地状态。安全，但把网络延迟暴露给了用户；失败时界面也不需要回滚，因为从来没变过。

乐观更新把顺序反过来：先假定成功，立即改本地状态，同时保存旧值；请求成功后什么也不用做，失败则用旧值恢复。用户看到的是即时反馈，代价是要自己处理回滚。

回滚要精确：只恢复本次提交涉及的字段（`liked`、`likes`），不能把整条数据覆盖回旧快照，否则会吃掉期间其他字段的更新。提交期间用 `pending` 标记禁用按钮，防止同一张卡片重复写入；不同卡片可以并行。

## 3. 方案：关键代码

```ts
async function toggleLike(id: number): Promise<void> {
  if (pending.value.includes(id)) return
  const post = posts.value.find((item) => item.id === id)
  if (!post) return

  // ① 提交前保存旧值，失败时按字段恢复
  const snapshot = { liked: post.liked, likes: post.likes }

  pending.value.push(id)
  // ② 立刻按「成功」改界面，用户不用等网络
  post.liked = !post.liked
  post.likes += post.liked ? 1 : -1

  try {
    await api.like(id, post.liked)
  } catch {
    // ③ 只回滚本次改动，不碰期间的其他更新
    post.liked = snapshot.liked
    post.likes = snapshot.likes
    toast.error('点赞失败，已撤回')
  } finally {
    pending.value = pending.value.filter((item) => item !== id)
  }
}
```

失败提示放在 catch 里，而不是在 `finally` 里判断状态；`finally` 只负责解除 pending，保证无论成功失败按钮都能恢复。

## 4. 数据对比

| 指标 | 等响应再改 | 乐观更新 | 测量方式 |
|------|------------|----------|----------|
| 点击后 40ms 的状态 | 未变（12） | 已变（13） | 读取按钮 `aria-pressed` 与计数 |
| 请求成功后 | 300ms 时变 13 | 300ms 时仍 13 | 等 450ms 后读取 |
| 请求失败后 | 保持 12 | 先 13，再回到 12 | 开「模拟接口失败」 |
| 回滚耗时 | — | 300ms（接口固定延迟） | 点击到计数恢复 |

测量说明：

- 环境：Chrome headless 155、1200×900、Vite dev；模拟接口固定 300ms 延迟。
- 取样：成功、失败、等响应三种路径各跑 3 次，状态变化一致，表中为一次结果。
- 本案例是行为指标；乐观更新不减少请求耗时，只把等待从「界面无反馈」变成「立即反馈 + 失败回滚」。

## 5. 追问与边界（面试高频）

- Q: 所有操作都适合乐观更新吗？ → A: 不是。点赞、收藏、勾选这类低风险可撤销操作适合；支付、扣库存、发消息这类不可逆或强一致操作不要用。
- Q: 回滚时数据已经被别的操作改过怎么办？ → A: 只回滚本次涉及的字段；复杂场景用操作日志或服务端返回的最终状态覆盖。
- Q: 为什么提交期间要禁用按钮？ → A: 防止连点产生多次请求；如果业务允许反复切换，就用请求编号保证最后一次生效。

踩坑：

1. 保存整条对象快照再整体覆盖 → 回滚会吃掉其他字段的更新。
2. 失败后只改数据不提示 → 用户看到数字跳回去，不知道为什么。
3. 不同卡片共用一个 pending 布尔值 → 一张卡片提交时所有卡片都被禁用。

边界：服务端可能拒绝（比如重复点赞）时，最好让接口返回最终状态，客户端以返回值校准；对强一致列表（订单、余额）应等响应或使用服务端推送，不要乐观更新。
